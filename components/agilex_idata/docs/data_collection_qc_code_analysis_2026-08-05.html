1. 结论摘要

当前系统不是“很多脚本共同组成一条链”，而是少数生产核心被大量旧入口、配置壳和特殊模式包围。

  • 真正负责采集的是 collect_mobile_episode_web.sh。
  • collect_mobile_pipeline_web_staged.sh 是总编排器，混合了网关、前端、ROS 状态机桥接和进程管理。
  • collect_mobile_pipeline_web_fixed_stage.sh 是 staged 的配置壳，并没有在程序内部真正消费固定阶段变量。
  • 质检后台核心是约 8200 行的 pipeline_web_app.py；四相机 Shell 也是配置壳。
  • 采集侧旧版 HDF5 和质检侧 aligned HDF5 构成两套转换链，同一 MCAP 经常重复转换。

最主要的技术债不是脚本文件数量，而是职责和数据契约重复：

  1. 同一份 MCAP 被两套已经分叉的转换代码处理。
  2. Shell 文件内嵌大量 Python、HTML、CSS 和 JavaScript。
  3. 商品、任务文本、相机、等级、失败原因存在多套来源。
  4. 采集与质检各自维护转换、审核、回放和元数据逻辑。
  5. 自动 QC 的 accepted 与人工 A/B/C/F 等级未统一。

3. 三个生产入口分析

3.1 单阶段入口：collect_mobile_pipeline_web_fixed_stage.sh

这是约 98 行的配置 wrapper，最终通过 exec 调用 staged 脚本。它负责：

  • 只接受 --fixed-stage 2。
  • 配置移动机器人、四相机、自动激活、开始/结束/就绪 ROS topic。
  • 默认关闭五阶段采集，使一次开始/结束形成单段 episode。
  • 指定商品库存和移动采集 YAML。
隐性问题：FIXED_COLLECTION_STAGE 没有消费者 Wrapper 导出了 FIXED_COLLECTION_STAGE=2，但当前代码中没有找到读取它的位置。因此“第二阶段”并不是平台内部强制的业务语义，而是依靠外部状态机和 topic 约定实现。

3.2 全阶段入口：collect_mobile_pipeline_web_staged.sh

这是超过 3000 行的总编排器，主要职责包括：

  • 加载 ROS2、相机环境，设置 ROS_DOMAIN_ID 和 FastDDS。
  • 启动采集核心、数据可视化和可选质检服务。
  • 端口探测、服务 readiness、日志重定向和进程组清理。
  • 内嵌 Python HTTP 反向代理以及完整 HTML/CSS/JavaScript 网关。
  • 内嵌约 1500 行 Python ROS2 状态机桥接。
  • 从商品配置动态生成阶段任务提示词。

五阶段业务定义：

  1. 底盘移动到货架。
  2. 左右夹爪抓取目标商品。
  3. 底盘移动到小车。
  4. 左右夹爪放置商品。
  5. 底盘返回起始位置。

ROS 桥接支持普通单段、五阶段、抓取/放置双数据集、人工审核门控、旧锁存事件清理，并维护 disabled / idle / starting / recording / saving / reviewing / error 等状态。

脚本名称与默认行为不一致 COLLECTION_STAGED_CAPTURE_DEFAULT=0 和 STATE_MACHINE_STAGED_DEFAULT=0，所以 staged 脚本默认并不会启用五阶段模式；需要页面勾选或环境变量显式打开。
  • 第四阶段主 topic 存在 state_maching 拼写错误，同时保留了正确 alias。
  • 部分网关面板有实现但当前导航不可达。
  • JavaScript 有重复监听片段。
  • 状态机规则与采集核心及 grasp_place_collection.py 有交叠。

3.3 四相机质检入口

collect_mobile_pipeline_qc_web_four_camera.sh 只有约 24 行，负责端口、四相机 robot profile、topic YAML、head 来源、camera layout 和相机选择 UI 等参数，随后调用基础启动器。

collect_mobile_pipeline_qc_web.sh 才负责解析数据目录、机器人、任务、repo、GPU、并发参数，选择具有不同依赖的 Python 环境，检查端口和依赖并启动 pipeline_web_app.py。

结论：四相机入口应保留用户可识别的启动方式，但实现应收敛为声明式 profile，而不是独立 Shell 逻辑。

4. 采集核心全部功能

collect_mobile_episode_web.sh 约 3500 行，是采集系统真正核心，同时承担配置、进程、ROS、业务、Web 和文件系统职责。

4.1 采集配置与后台处理

  • 管理数据目录、episode 编号、移动底盘和 staged 模式。
  • 选择相机、手臂、底盘、升降 topic 配置。
  • 控制是否转换、质检、导出 LeRobot。
  • 默认录完转旧版 HDF5、执行采集侧轻量 QC；默认不导出 LeRobot。
  • 默认后台处理，支持有限并发；通过脚本自递归的 PROCESS_ONLY 模式实现。

4.2 采集前硬件检查

check_mobile_topics.sh 检查 4 个 RGB 相机、左右主从臂、左右末端位姿、localization/odom、底盘状态/动作、升降状态/动作及服务。检查不仅验证 topic 存在，还验证消息类型、payload、数值有限性和实际数据到达。

camera_timestamp_health.py 订阅四路压缩图像，计算消息到达时间与 header 差、P90 延迟、多相机时间戳中位差和最小样本数；异常时 fail-closed，拒绝采集。

4.3 ROS2 MCAP 录制

移动采集 launch 实际启动 Python 版 record_mcap.py，而非历史 C++ dataCapture.cpp。录制器：

  • 从 YAML 读取 topic，使用 rosbag2 SequentialWriter 写 MCAP。
  • 提供 /data_tools_dataCapture/capture_service。
  • 每秒统计 topic 频率并生成 capture_health.json。
  • 记录覆盖率、频率失败和最大相机帧间隔。
覆盖风险启动已有 episode 时，录制器存在直接删除旧 episode 目录的逻辑，需要在重构中改为显式冲突和可恢复操作。

4.4 元数据与采集侧审核

collection_episode_metadata.py 维护商品目标、左右手对象、scene/items、task、A/B/F、失败原因和审核状态，并在 MCAP 与旧版 ALOHA HDF5 之间同步 sidecar。F/丢弃会删除 raw 与 ALOHA，episode 编号可能复用，未审核不能进入下一条。

4.5 Web API、回放与安全

核心 API 包括 /status、/config、/start、/stage、/save、/abandon、/check、/quality/review，以及回放、急停、复位和退出接口。

平台支持旧 HDF5、aligned HDF5、LeRobot 的可视化和移动机器人真机回放；软件急停可发布零速度、保持机械臂/升降机构、停止采集和回放并丢弃当前 episode。

当前状态由 FIFO、JSON 文件、进程内状态和控制文件共同维护，这是竞态、残留状态和恢复复杂度的主要来源。

6.3 自动质检规则

run_quality_pipeline.py 负责单集/批量任务和并行处理，episode_io.py 适配 G2、ALOHA HDF5、parquet 和 raw，quality_pipeline/qc.py 执行以下检查：

  1. state 维度。
  2. action 维度。
  3. NaN/Inf 等非有限数值。
  4. 时间戳单调性和最大间隔。
  5. 实际 FPS。
  6. 相机帧完整性。
  7. 连续重复/修复相机帧。
  8. 轨迹时长。
  9. 关节、状态跳变和运动稳定性。
  10. action、state、base 连续静止段。
  11. 夹爪活动量。

四相机 ALOHA 核心契约为 state 21 维、action 18 维、最低约 29 FPS、时长约 4–10 秒、相机缺帧比例阈值和最长静止帧约 15。评分从 100 开始，硬失败令 accepted=False。

8. 关键冗余、缺陷与风险

8.1 自动 QC 与 A/B/C/F 等级脱节

自动失败的 episode 仍可能默认成为 A 当前自动质检产生 accepted、score、warnings、errors；人工审核产生 A/B/C/F。最终整理逻辑中，如果没有人工等级且没有显式 F，episode 即使 accepted=False 也可能默认标为 A。C 基本是人工等级，自动 QC 没有明确等级映射。

建议拆为三个正交字段：

qc_status:        PASS | FAIL | NEED_REVIEW
manual_grade:    A | B | C | F | null
lifecycle_status: RAW | CONVERTED | QC_DONE | REVIEWED | EXPORTED

8.2 商品和任务存在多套来源

当前来源至少包括 collection_targets.py、market_scene_inventory.json、task_names.py、robot profile 的 YOLO alias、HDF5 task、episode_meta items/task 和 LeRobot tasks/mapping。各列表商品集合并不完全一致。

这会直接导致“任务写王老吉，但 items 或前景是其他商品”一类错误。修结果不能消除源头，应建立唯一 products.yaml，包含 canonical id、中英文名、alias、视觉类名、库存和标准任务模板。

8.3 相机契约重复定义

相机信息分散在录制 YAML、topic preflight、时间戳脚本、旧版 HDF5 verifier、质检 topic YAML、camera layouts、robot profiles、转换 meta 和 LeRobot converter。相机增加或重命名需要多处同步，易导致三相机 front/global 混用。

8.4 失败原因和人工审核规则重复

A/B/F 或 A/B/C/F 的原因、中文文本和字段定义至少重复在采集 JavaScript、collection metadata、mcap converter、HDF5 replay 和 pipeline Web 中，应收敛为一个版本化 schema。

8.5 Shell 已成为应用运行时

三个大 Shell 同时承担环境管理、HTTP 服务、ROS node、业务状态机和前端构建。staged、旧 unified、inference 多套 orchestrator 又重复实现相似网关和进程管理。这使单元测试、类型检查、IDE 导航和异常恢复都非常困难。

8.6 Web 安全与破坏性操作

质检 Web 默认监听 0.0.0.0，提供删除 HDF5、裁剪、修改等级、重编号和启动处理等接口，但未见正式认证和 CSRF 防护。

录制覆盖、采集丢弃、HDF5 删除、原地裁剪和重编号都可能修改多类文件，需要操作审计、权限控制和恢复策略。

8.7 静止裁剪不是跨文件事务

裁剪依次修改 HDF5、多个 MP4 和 meta。任一步中断会留下 HDF5 已裁、视频未裁或临时视频残留的“半裁剪”状态。现有 guard 能在下一次运行时检测，但不能让第一次更新原子化。

9. 真正需要保留的能力

重构不应以“保留哪些大脚本”为目标，而应保留下列业务能力，并允许旧脚本退出：

10.1 核心原则

  • Raw MCAP 永远只读，是原始真值。
  • 正式中间格式只保留 aligned HDF5。
  • 写入临时目录，全部成功后原子 rename。
  • 处理可从 MCAP 幂等重跑，不依赖半成品。
  • 所有采集模式由 YAML profile 表达，不复制 Shell。
  • 商品、相机、等级和原因各只有一个 source of truth。
  • 自动 QC、人工等级、生命周期状态分开。
  • 前端不嵌入 Shell；ROS bridge 是独立 Python node。
  • 后台任务使用可持久化 job manifest，而不是大量环境变量、FIFO 和全局 JSON 混合状态。

11. 建议实施顺序

  1. 冻结行为：恢复并补齐采集元数据、fixed stage、任务一致性、裁剪事务和状态恢复测试；准备少量 golden MCAP/HDF5。
  2. 统一契约：定义 Episode、Task、Product、Camera、Quality/Grade 和 lifecycle schema。
  3. 先搬后改：把 staged 内嵌 Python 网关和 ROS bridge 原样提取为独立模块，暂不改变行为。
  4. 拆采集核心：将 Web UI、API、ROS adapter、进程管理、元数据和状态机从大 Shell 分离。
  5. 统一转换：选择 aligned HDF5 为 canonical，停止同一 MCAP 双重转换。
  6. 统一审核：统一 task/items/product、自动 QC、人工等级和失败原因。
  7. 模式配置化：单阶段、五阶段、抓取放置、推理、左臂、相机布局全部 profile 化。
  8. 合并平台：合并重复的 HDF5/LeRobot 浏览与回放页面，添加认证和权限。
  9. 安全改造：为裁剪、删除、重编号、等级迁移增加事务、审计和可恢复机制。
  10. 最后归档：经过外部使用审计和至少一个生产周期观察后，再移除历史 Shell。

12. 验证和分析边界

现有相关测试结果 运行当前仍存在的自动评级、商品下拉、抓取/放置、可选相机 QC、轨迹时长和状态性能测试：109 passed in 27.05s。

但当前工作区存在多项未提交修改，并且一批采集元数据、fixed-stage、任务一致性和平台操作测试处于删除状态。因此 109 个测试通过不能证明整条生产链已具备安全重构保护，只能说明当前剩余测试未失败。

本报告是代码静态分析和局部测试结果，不包含对所有采集机器上的 systemd、cron、桌面快捷方式、外部仓库和操作员私有脚本的审计。历史脚本的最终删除必须补充这一步。

最终判断

当前系统功能完整，但边界不清。最优先拆分的是 collect_mobile_episode_web.sh、collect_mobile_pipeline_web_staged.sh 和 pipeline_web_app.py；最优先统一的是 MCAP 转换链、商品/任务元数据、相机 profile 和质量状态模型。旧 Shell 应在这些能力被新模块接管且外部调用审计完成后再归档。
