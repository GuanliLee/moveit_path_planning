# 轨迹时长质检与页面切换性能设计

## 目标

为数据质检服务增加轨迹过短、过长检测，在质检报告和网页中给出明确提示；在质检页下方展示当前质检项目；缩短三路与四路相机配置切换时报告和 HDF5 状态的加载时间。

## 规则

- 轨迹时长使用 episode 首尾时间戳计算的 `duration_sec`。
- `duration_sec < 4.0` 时状态为 `warn`，提示“轨迹过短”。
- `duration_sec > 10.0` 时状态为 `warn`，提示“轨迹过长”。
- `4.0 <= duration_sec <= 10.0` 时通过。
- 时长异常只扣 5 分并给出警告，不单独造成硬失败。
- 三路和四路 ALOHA profile 使用相同阈值；G2 保持原有最短时长规则，避免扩大本次改动范围。

## 报告与页面

- `qc_report.json` 的 `duration` 检查同时包含 `duration_sec`、`min_duration_sec`、`max_duration_sec` 和判定原因。
- Markdown 报告显示实际时长及允许范围。
- 网页 episode 表格的 warning 列显示“轨迹过短/过长、实际时长、阈值”。
- 质检报告面板下方新增“质检项目”区，显示各规则名称、检查内容和关键阈值，使用紧凑网格展示。
- 页面展示项目来自后端返回的 profile 规则，防止界面文案与实际阈值不一致。

## 性能方案

采用元数据优先加服务端缓存的组合方案：

1. 扫描 HDF5 episode 时，只有 sidecar 缺少帧数或 FPS 才打开 HDF5 文件估算，避免每次切换逐个打开全部 HDF5。
2. 每个 `qc_report.json` 在一次状态请求内只解析一次，warning 和概览共用解析结果。
3. 对 `/api/status` 结果做按相机模式及路径隔离的 5 秒缓存，最多保留 8 个数据集状态；缓存键包含 HDF5、QC、LeRobot、数据集、profile 和相机配置。
4. 缓存有效性由关键目录及摘要文件的修改时间指纹决定；质检、删除、修复或人工等级保存后主动清理缓存。
5. 前端切换时取消上一条未完成请求，并忽略过期响应，避免快速切换造成旧模式覆盖新模式。

缓存仅保存派生状态，不写入业务数据。三路和四路使用不同键，不能互相复用报告。

## 测试与验收

- 单元测试覆盖过短、边界内、过长三种时长。
- 报告格式测试覆盖“轨迹过短”和“轨迹过长”提示。
- Web 测试覆盖质检项目展示、元数据优先读取、缓存命中、模式隔离和数据变更失效。
- 运行现有相关测试与语法检查。
- 使用当前约 160 条 episode 的三路、四路数据分别测量 `/api/status`；重复切换请求应明显快于修改前，并保持报告目录和 episode 数一致。
- 验证通过后按现有环境变量和命令重新启动 `0.0.0.0:8001` 服务，并检查健康响应。
